- 不落盘 HTTP 预取独立于持久缓存下载器，失败时不阻断播放，也不创建缓存任务和锁文件。

- 用户脚本日志生成脱敏快照，动态标题、字幕、文件名和 STRM 路径使用文本节点。

## 3. 当前运行边界

ETLP 仍是本地播放辅助服务。浏览器脚本向本机 HTTP 服务发送请求，服务解析 Emby、Jellyfin 或 Plex 数据，选择本地播放器，并可选地使用 CloudDrive2 gateway、Emby 会话和远程控制通道。

当前约束保持不变：

1. 本地 HTTP 默认监听回环地址；非回环监听需要强 token。
2. Emby/Plex 请求必须先完成解析，再创建后台播放线程。
3. 远程控制失败时降级为普通播放和最终进度回传。
4. STRM 预热和 CloudDrive2 解析属于 best-effort，失败时保留原路径判断和回退逻辑。
5. `stable` 是稳定频道，`beta` 是测试频道，`main` 只用于上游同步。
6. 更新器按安装包频道选择 GitCode Release，失败时回退 GitHub，并校验 ZIP、sidecar 和可选 `release-plan.json`。

### 阶段 B：beta 成品与客户端验收

此阶段验证 S46–S52 及后缀修复的组合行为，不再安排重复实现已有功能。

- 在频道分支完成 Windows 成品检查，核对 Python 3.9 x86 包内依赖、离线启动、入口脚本和频道信息。
- 检查重复启动、已有播放时 409 提示、快速退出、端口冲突和关闭后再次播放。
- 检查 Emby 多版本 STRM、CD2 成功/失败回退、缓存失败后网络播放、连续播放、字幕、章节和最终进度。
- 对每项记录版本、场景和结果；用户曾验证 sidecar 映射后可播放，不代替完整的多版本与生命周期验收。
- beta 验收通过后再形成 stable 推进建议；保留上一个已验收版本和精确回退步骤，核查两平台资产与旧更新器兼容资产。

阶段出口：自动化、包内运行时和适用客户端场景分别通过，残余风险有明确记录。
历史 `/playMediaFile` helper 不属于主播放 lease 保证，本轮不扩大其行为。
stable 日常使用和更新下载问题按实际反馈排查；本计划不自动创建监控或定时任务。

### 阶段 C：播放失败反馈

当前前端错误提示仍较粗，后续需要把请求接收和播放器实际启动结果分开：

- 区分本地服务不可达、协议拒绝、配置无效、播放器路径错误、媒体打开失败和 CD2 回退。
- 为后台起播任务增加有限时长的状态反馈。
- 保留可操作的下一步，例如检查播放器路径、配置路径映射或重新启动本地服务。
- 避免把所有错误都提示为“本地服务未运行”。

建议拆分为错误分类与协议、有限任务状态、前端提示三步。阶段出口是路径错误、起播失败和
超时能够在前端得到对应反馈，状态会过期回收，日志不泄露路径或认证数据。开始实现前需确认
状态查询协议、超时与保留时长，再形成独立 Stack 计划。

### 阶段 D：更新安装恢复

现有更新器已经具备下载校验、ZIP 安全检查和配置保护，后续要解决替换过程的中断风险：

- 暂存解压并完成全部校验后再进入替换阶段。
- 替换前保存明确的旧版本备份。
- 对文件占用、磁盘空间不足和复制中断提供恢复路径。
- 下次启动时识别未完成更新并恢复到完整版本。
- 通过故障注入测试验证恢复和回滚。

建议顺序为暂存校验、替换记录与备份、启动恢复、故障注入。阶段出口是任一步骤中断后仍能
恢复到完整旧版或完整新版，用户配置保留。备份位置、保留规则、恢复触发时机先设计确认。

### 阶段 E：Python 运行时评估

当前发布包继续使用 Python 3.9 x86 embedded runtime。迁移前需要独立比较 Python 3.13/3.14 的 Windows embedded 包、x64 兼容性、依赖 wheel、ctypes 行为、播放器进程管理和离线启动。

运行时迁移必须保留旧版回退包，不能和播放会话重构混在同一个版本中。

本阶段首先交付兼容性矩阵和迁移建议；不预先认定目标 Python 版本或 CPU 架构。
通过包内依赖、ctypes、播放器管理、离线启动和升级回退验证后，才决定是否实施迁移。

### 阶段 F：播放身份与传输模型

这是中期架构工作，按适配层逐步推进：

- 媒体身份使用服务器标识、ItemId 和 MediaSourceId。
- 每次加入播放列表生成独立 `entry_id`，允许同一媒体重复入列。
- 每次实际播放生成 `session_id`，集中持有停止、预取和进度状态。
- 分开描述 `source_kind`、`transport`、字幕来源和章节来源。
- 保留 `mount_disk_mode` 作为兼容适配，先补组合回归，再替换调用点。

在身份和状态模型迁移完成前，不对多播放器并行播放作能力承诺。

建议顺序为组合回归、身份适配、session 状态归属、传输描述与调用点迁移。
每步保持现有行为可用；公共字段、状态所有权和兼容期限需独立设计，适用时创建 ADR。

### 阶段 G：配置和模块整理

按收益逐步推进，不做一次性重构：

- 增加脱敏的轻量自检，检查配置文件、播放器路径、缓存目录、CD2 token/path_map、版本和频道。
- 明确代理的“自动、指定、直连”三种语义。
- 评估 `version_filter`、`enable_host` 和 CD2 配置模式的可读性与兼容规则。
- 将配置导入副作用逐步移出 `configs.py`。
- 按边界提取元数据获取、版本选择、预取、进度回传和播放器适配模块。
- 核查用户脚本 MIT 声明与仓库 Apache-2.0 许可证的来源和归属。

优先做能帮助定位故障的自检，再按实际收益安排配置语义与模块提取。许可证项先核实来源，
不直接修改声明。每项独立验收；配置语义调整和模块重构不能仅凭本路线图直接实施。

## 5. 推荐顺序和发布门槛

推荐顺序如下：

1. 完成 S49 → S50 → S51 三项修复和集成回归；S52 播放列表时序修复已完成。
2. 完成当前 beta 成品与真实客户端验收，再决定是否进入 stable。
3. 完善播放失败反馈。
4. 实现更新中断恢复并做故障注入。
5. 单独完成 Python runtime 兼容性评估。
6. 在组合回归保护下逐步迁移播放身份和传输模型。
7. 按实际收益整理配置和模块。

每个版本进入发布前都应满足：

- 相关自动化测试通过，且与上一版基线对比没有新增失败。
- Windows 打包、sidecar、Release plan 和包内频道元数据一致。
- 关键播放器和媒体路径完成适用范围内的验收。
- 发布后可从 GitCode 和 GitHub 下载同一 SHA-256 的 ZIP。
- 有明确的回滚版本和回滚步骤。

实现阶段由主线程负责设计、派发、审核与集成，边界明确的编码任务交给独立 worktree 中的
`luna_worker`；中期阶段进入实现前补齐各自 PR Stack 契约。S52 已按独立 Stack 完成并发布，
S49–S51 仍需按本计划单独执行；后续外部操作仍按当次明确授权执行。

## 6. 当前不纳入计划的能力

- 同步观看房间、参与者管理和跨设备跟随播放。
